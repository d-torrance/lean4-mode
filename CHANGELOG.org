#+title: Lean4-Mode - Changelog
#+language: en

* Version 2.0.0

Lean4-Mode now uses [[https://www.gnu.org/software/emacs/manual/html_node/eglot/][Eglot]], the LSP client built into Emacs, instead of
lsp-mode.  Everything reaches the user through the extension points
Emacs already has, so the interfaces they already use apply:
diagnostics through Flymake, completion through
~completion-at-point-functions~, hover through ElDoc, jumping through
xref, project roots through =project.el=.

** Breaking

- lsp-mode is replaced by Eglot.  Requires Emacs 29.1 or later.  Any
  lsp-mode configuration for Lean can be removed.  Version =1.1.2=
  remains tagged for anyone not ready to move.
- Maintenance has moved to [[https://github.com/d-torrance/lean4-mode][d-torrance/lean4-mode]];
  a package recipe pointing at the old repository will not see this
  release.
- Dependencies: =dash= and =compat= are gone; =eri= and =magit-section=
  (3.3.0 or later) remain.  Indentation cycling now comes from the =eri=
  package on Melpa, which is the upstream of the copy this package used
  to vendor, so ~lean4-eri-indent~ and ~lean4-eri-indent-reverse~ are
  now ~eri-indent~.
- Diagnostics come from Flymake rather than Flycheck.
- The ~lean4-keybinding-*~ options are gone, and with them the
  =lean4-keybinding= customize group.  Keys live in ~lean4-mode-map~ and
  are rebound the ordinary way.
- ~lean4-mode-hook~ is an ordinary mode hook again; whether the server
  starts automatically is now ~lean4-auto-start-server~, default =t=.
- ~lean4-extra-arguments~ is renamed ~lean4-server-arguments~, with the
  old name kept as an alias.
- Lean 3 autodetection is removed, along with ~lean4-autodetect-lean3~.
  It ran =lean -v= on every =.lean= file opened.
- ~lean4-syntax-table~ is renamed ~lean4-mode-syntax-table~, the name
  the major mode conventions ask for, with the old name kept as an
  obsolete alias.  The empty ~lean4-abbrev-table~ is gone; the mode now
  uses the ~lean4-mode-abbrev-table~ that ~define-derived-mode~ makes
  for it, which is where =M-x edit-abbrevs= looks.
- ~lean4-memory-limit~ and ~lean4-timeout-limit~ are gone.  Neither was
  read by anything in version 1.
- The goal display's two debounce options,
  ~lean4-info-buffer-debounce-delay-sec~ and
  ~lean4-info-buffer-debounce-upper-bound-sec~, are replaced by the one
  ~lean4-info-debounce-delay~.
- =lean4-debug.el= and =lean4-dev.el= are gone, and with them =M-x
  lean4-turn-on-debug-mode=, =M-x lean4-turn-off-debug-mode=, =M-x
  lean4-diff-test-file= and the =*lean4-debug*= buffer.
- ~lean4-info-mode~ is now the goal display's own major mode, derived
  from ~magit-section-mode~; in version 1 it was a ~prog-mode~
  derivative used only to fontify goal text.  The display is read-only
  and its mode line reads "Lean Goal".  The buffer is still =*Lean
  Goal*=.
- The abbreviation table is refreshed from vscode-lean4, which changes
  what four abbreviations insert: =\n= now gives a literal =\n= rather
  than ¬, =\!= gives ¬ rather than ¡, and =\dot= and =\cdot= give ·
  rather than ⬝.  Seven abbreviations are gone and thirty-one are new.

** Added

- The goal display opens by itself when a Lean file is visited, as VS
  Code's InfoView does.  It is displayed rather than selected, and goes
  through ~display-buffer~, so =display-buffer-alist= governs where it
  lands; ~lean4-info-auto-open~ turns the automatic opening off and =M-x
  lean4-info-open= opens it by hand.
- Interactive goals.  Goals arrive as trees in which every subterm is
  labelled, so point can rest on a subterm and get its type through
  ElDoc, or jump to its definition through xref.  The extent of the
  subterm under point is highlighted, and what Lean reports as changed
  since the previous goal is faced as a diff.  Setting
  ~lean4-info-interactive~ to =nil= asks for plain-text goals instead.
- The whole display is built from ~magit-section~: every part of it
  folds with =TAB=, the fold indicators are drawn by ~magit-section~
  itself, and folds survive the rebuild that a new goal causes.  It has a menu of its own,
  offering the same controls as the Lean menu -- they all work from
  either buffer -- alongside what only the display can do.  Menu entries
  say what pressing them will do next.
- Any number of pinned positions, each a section of its own above the
  one following point, so several goals can be watched at once.  A pin
  is a marker, so it follows its declaration through an edit and stays
  on display after moving to another file.  Pinning no longer stops the
  display following point.  =M-x lean4-info-unpin-all= removes them all.
- Pausing, separately, for the display as a whole, for each pinned
  position, and for the file's message list.  A paused section can be
  brought up to date without unpausing it, which is VS Code's "refresh
  paused state".
- Messages are placed by Lean's own notion of which declaration they
  belong to, so one about a multi-line declaration stays visible while
  point moves through it.  Those covering point are listed under
  =Messages= within the position's heading; every message in the file is
  listed under =All messages=, ordered either by nearness to point, as
  VS Code has it, or by position in the file
  (~lean4-info-message-order~, or =C-c C-o=).  Both headings count what
  is in them by severity -- =All messages (1 ⊗  5 ⓘ)=.  Each message is
  a foldable section headed by its file, line and column, with a control
  that sends point there, and terms inside a message are as interactive
  as terms inside a goal.
- Collapsible traces.  Lean does not send the children of a trace node
  until asked, so unfolding one fetches it; children are indented under
  the node they belong to.
- Every control in the display is a real button, so =RET= presses the
  one at point -- or goes to the position a message heading names -- and
  ~forward-button~ and ~push-button~ find them.  =mouse-1= presses a
  control and elsewhere just sets point, which is how a subterm is put
  under ElDoc.  Every control has a key and a menu entry as well, so
  none of them needs a mouse, and inside a pinned section the keys mean
  that section.  The glyphs are chosen to suit each frame, and
  ~lean4-info-pin-icon~ and its six siblings override them.
- Where there is nothing to report the display says =No info found.=
  rather than showing a bare heading.
- Diagnostics understand Lean's own extensions: ~fullRange~, which is
  what places a message against its declaration, ~isSilent~, so what
  Lean means for the goal display alone -- the completed-proof report
  among it -- is kept out of the editor, and ~leanTags~, which marks a
  finished declaration.  ~lean4-flymake-minimum-severity~ decides what
  reaches Flymake at all, default =warning=, so trace output and notes
  no longer bury the errors; ~lean4-show-goals-accomplished~ puts a =✓=
  against a completed proof; and =M-x lean4-diagnostics-next-sorry=
  moves between the declarations that still use =sorry=.
- Indentation that guesses from the layout, with =TAB= cycling through
  the alternatives when the guess is wrong.  ~lean4-indent-offset~ sets
  the width of a level, and ~lean4-indent-function~ restores the
  previous cycle-only behaviour.
- Completion through ~completion-at-point-functions~ from three sources:
  the Unicode abbreviations, so =\al= offers =\alpha=; Lean's keywords,
  which the server offers nothing towards for a bare word; and the
  server's own, rewrapped so that it is not exclusive -- where Lean
  answers nothing, whatever else is configured is still reached.
- Semantic highlighting, when the available Eglot provides it; Eglot
  gained semantic tokens in version 1.20.  Expect keywords, and =sorry=
  and its relatives through Lean's ~leanSorryLike~ token type, rather
  than colour for every identifier.
- Where the server is started from is worked out rather than guessed: a
  file inside a Lake package is served by =lake serve= from the
  workspace root, and one outside any package by =lean --server= with
  elan's default toolchain, as VS Code serves both.  Discovery walks to
  the outermost =lean-toolchain=, so a package vendored under
  =.lake/packages= is elaborated by the toolchain of the project that
  pulled it in, and ~lean4-workspace-roots~ and
  ~lean4-workspace-exclusions~ override where it looks.  =C-c C-r=
  restarts the server; version 1 had an option for that key but never
  bound it.
- =M-x lean4-diagnose= reports how things are set up: the versions of
  Emacs and each dependency, the Lean and Lake executables found and
  their versions, the workspace root and its toolchain, the command the
  server was started with, and the current diagnostics.  The counterpart
  of VS Code's "Show Setup Information".
- Mathlib's build cache can be fetched, through =lake exe cache get=:
  ~lean4-lake-fetch-cache~ (=C-c C-p C-c=) for the whole package,
  ~lean4-lake-fetch-file-cache~ (=C-c C-p C-f=) for the current file and
  what it imports, and ~lean4-lake-fetch-open-file-caches~ for every open
  Lean file in the package.  The counterparts of VS Code's three "Fetch
  Mathlib Build Cache" commands.  The Lean menu gains a =Project=
  submenu holding these and =lake build=.
- Eight settings deciding how much of a goal to show, the same eight
  VS Code gathers behind the cog in its InfoView: goal names, emphasis on
  the first goal, the target above the hypotheses, and hiding type
  assumptions, instance assumptions, inaccessible assumptions or
  let-values, along with whether the expected type is shown, folded or
  left out.  Each is an option, a command and a checkbox in both menus,
  under =How much of a goal to show=; every default is VS Code's, so the
  whole goal is shown until asked otherwise.  Goals are now kept as Lean
  sent them and rendered on the way into the buffer, so a change costs a
  redraw rather than another request -- and so reaches a pinned or paused
  section, where re-fetching would be the wrong thing.
- The goals at point are headed =Tactic state=, with the number of them
  on the line below, both as VS Code words and places them.  The heading
  read =Goals:= and there was no count.  A single goal is counted too, so
  the line is there on every proof; a finished proof still reads =goals
  accomplished=, where VS Code counts nothing either.  The expected type
  is headed =Expected type= rather than =Expected type:=, neither heading
  taking a colon in VS Code.
- ~lean4-lake-clean~ deletes the package's build artefacts and
  ~lean4-lake-update-dependency~ updates one dependency, offering the
  package's direct Git dependencies for completion from
  =lake-manifest.json=.  Both ask first, as VS Code's counterparts do,
  and both join the =Project= menu.  Manifest versions before and after 7
  are read, the shape having changed at that point.
- The module hierarchy, in a =*Lean Module Hierarchy*= buffer:
  ~lean4-module-hierarchy~ shows what this file's module imports and
  ~lean4-module-hierarchy-inverse~ what imports it, both as a
  ~magit-section~ tree that folds with =TAB=, visits with =RET= and
  refetches with =g=.  ~lean4-module-copy-name~ copies the module's name,
  as VS Code's "Copy Module Name" does.  A level is fetched as it is
  opened, Mathlib's import graph being far too large to ask for at once,
  and a module already shown further up is marked rather than expanded.
  Import modifiers -- =private=, =all=, =meta= -- are shown for modules
  using Lean's =module= keyword.  Needs a built project: the server
  answers from the =.ilean= index a build leaves behind.
- The goal display can be copied out of: ~lean4-info-copy-state~ and
  ~lean4-info-copy-message~ to the kill ring, and
  ~lean4-info-copy-to-comment~ into a =/- -/= block above the line point
  is on, indented with it.  The counterparts of VS Code's "Copy State",
  "Copy Message" and "Copy Contents to Comment".  The state is copied in
  full, whatever the display is set to hide, as VS Code copies it.
- ~lean4-lake-build~ now does what VS Code's "Build Project" does, rather
  than a bare =lake build=: =lake resolve-deps=, then =lake exe cache
  get= where Mathlib's =cache= executable exists, then =lake build=, each
  conditional on the one before and all reporting into one compilation
  buffer.  On a project depending on Mathlib the cache step is the
  difference between minutes and hours; where there is no such executable
  it is skipped without complaint, but a download that fails stops the
  build instead of leaving it to compile Mathlib locally.  For a bare
  =lake build=, use =M-x compile=.
- =M-x lean4-loogle-search= searches Mathlib with
  [[https://loogle.lean-lang.org][Loogle]], which matches by shape rather than by name.  Results are listed
  in a =*Lean Loogle*= buffer with their module and type; =RET= opens a
  result's documentation, =w= copies its name, =g= asks again, and a
  spelling suggestion from Loogle is a button that searches for it.  The
  query is read with the Lean input method inherited, so =\alpha= becomes α
  in the minibuffer, Loogle's syntax leaning on notation.  The counterpart
  of VS Code's "Search With Loogle".
- Four commands for choosing which Lean to use, the counterparts of VS
  Code's: ~lean4-select-project-toolchain~ writes the project's
  =lean-toolchain=, ~lean4-select-default-toolchain~ runs =elan default=,
  ~lean4-update-release-channel~ fetches the newest version of a channel
  that has moved on, and ~lean4-uninstall-toolchains~ removes installed
  ones.  The versions offered include the released ones that are not
  installed, fetched from =release.lean-lang.org= as VS Code fetches them,
  each marked accordingly and ordered newest first.  All four need elan 4
  or later, as VS Code's do.  Installing elan itself is deliberately not
  offered.
- A test suite: 288 unit tests, and 37 end-to-end tests that run against
  a real Lean server.  Both run in CI.

** Fixed

- A Lake package is recognised by its =lakefile.toml= as well as by a
  =lakefile.lean=.  Only the latter was looked for, so a package using
  the TOML form was treated as no package at all.
- The server command is chosen from the workspace root rather than by
  running =lake --version= in whatever directory happens to be current,
  which asked the wrong toolchain in a multi-toolchain checkout.
- File watching is off by default, behind ~lean4-enable-file-watchers~.
  Lean asks to watch every =*.ilean= file, which on Mathlib is tens of
  thousands of them.
- The goal display keeps its place when it refreshes.  It is rebuilt from
  scratch whenever the goal changes, which threw a reader part-way down a
  long goal to the bottom of the buffer.
- Two messages about one declaration are listed in the order they were
  written.  They were ordered by where each message ends rather than
  where it starts, which put them the other way round.
- Menu entries pointed at a customize group that did not exist, and the
  README documented commands and a buffer name that did not either.
- Opening a Lean file no longer changes anything outside its own buffer.
  It set the global ~default-input-method~, so =C-\= then toggled the
  Lean input method in every other buffer, and it emptied
  ~compilation-mode-font-lock-keywords~, so every later =M-x compile=
  buffer went unfontified.
- Electric indentation is declined with ~electric-indent-inhibit~
  instead of switching ~electric-indent-local-mode~ off, which took a
  minor mode away from anyone who had turned it on.
- Opening a Lean file no longer builds the dependencies it imports.  Lean
  decides that from a ~dependencyBuildMode~ field on
  =textDocument/didOpen=, and reads its absence as "always" for the
  benefit of clients written before the field existed -- so sending
  nothing, as this package did, meant that visiting one file of Mathlib
  could start a build of everything it imports.  Ordinary opens now say
  "never" and =C-c C-d= says "once", which is what VS Code sends for each;
  set ~lean4-automatically-build-dependencies~ to =t= for the old
  behaviour, the counterpart of VS Code's
  =lean4.automaticallyBuildDependencies=.  "Once" also reverts to "never"
  on the server, so a file worker that crashes after a =C-c C-d= no
  longer sets the build going again.

* Version 1.1.2

- Fix occasional errors like "The connected server(s) does not support
  method =$/lean/plainGoal=" by not wrapping invocations of
  ~lsp-protocol~ macro into ~eval-when-compile~ but rather into
  ~eval-and-compile~.  Thus, the methods should now work, no matter
  whether Lean4-Mode was loaded by interpreting =.el= Elisp code or by
  loading compiled =.elc= or =.eln= files.  ([[https://github.com/leanprover-community/lean4-mode/issues/54][Bug#54]], [[https://leanprover.zulipchat.com/#narrow/channel/468104-Emacs/topic/lsp-mode.20errors.20due.20to.20list.20!.3D.20hash-table][Zulip discussion]])

* Version 1.1.1

  =lean4= group.  To customize Lean4-Mode, you now need to type =M-x
  customize-group RET lean4 RET=.
