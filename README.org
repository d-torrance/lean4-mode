This package extends [[https://www.gnu.org/software/emacs/][GNU Emacs]] by providing a major mode for editing
code written in version 4 of the programming language and theorem
prover [[https://lean-lang.org][Lean]].

The Lean4-Mode source code is developed at [[https://github.com/d-torrance/lean4-mode][Github]] and its issues
tracked there too.  Further discussions and question-answering takes
place in the [[https://leanprover.zulipchat.com/#narrow/channel/468104-Emacs][#Emacs channel]] of Lean's Zulip chat.

This continues the [[https://github.com/leanprover-community/lean4-mode][lean4-mode]] developed under the
leanprover-community organization; see [[*Acknowledgements]].

For legacy version 3 of Lean, use the archived [[https://github.com/leanprover/lean3-mode][Lean3-Mode]] (also known
as /Lean-Mode/).

* Installation

** Requirements

- [[https://lean-lang.org/lean4/doc/setup.html][Lean]] version 4, normally installed through [[https://github.com/leanprover/elan][elan]]
- GNU Emacs version 29.1 or later
- The Emacs packages [[https://github.com/agda/agda][eri]] and [[https://github.com/magit/magit/blob/main/lisp/magit-section.el][magit-section]], both on [[https://melpa.org/#/getting-started][Melpa]]

Eglot is used for the language-server connection, and is built into
Emacs 29 and later, so nothing needs installing for it.  See
[[*Semantic highlighting]] for one feature that a newer Eglot than the
bundled one provides.

magit-section 3.3.0 is enough, and is what Debian and Ubuntu ship as
=elpa-magit-section=.  If you have it, do not install a newer one on
this package's account: Magit depends on the matching version of
magit-section, so upgrading only that one breaks Magit.  Both versions
are tested, including against a live Lean server.

** From source

Clone the repository and add it to the ~load-path~:

#+begin_src elisp
(add-to-list 'load-path "~/path/to/lean4-mode")
#+end_src

Lean4-Mode is then enabled automatically for files with the =.lean=
extension.  Loading it eagerly is only necessary in order to customize
variables before a Lean file is opened:

#+begin_src elisp
(require 'lean4-mode)
#+end_src

** With a source-based package manager

List the ="data"= directory in the recipe: it holds the table of
Unicode abbreviations, without which the input method has nothing to
offer.  If loading is deferred, specify ~lean4-mode~ as a =:command=.

*** Native =:vc= (Emacs 30 or later)

#+begin_src elisp
(use-package lean4-mode
  :commands lean4-mode
  :vc (:url "https://github.com/d-torrance/lean4-mode.git"
       :rev :last-release
       ;; Or, for the bleeding edge:
       ;; :rev :newest
       ))
#+end_src

*** Doom-Emacs

#+begin_src elisp
(package! lean4-mode
  :recipe (:host github
           :repo "d-torrance/lean4-mode"
           :files ("*.el" "data")))
#+end_src

*** Straight

#+begin_src elisp
(use-package lean4-mode
  :commands lean4-mode
  :straight (lean4-mode :type git :host github
                        :repo "d-torrance/lean4-mode"
                        :files ("*.el" "data")))
#+end_src

** Upgrading from version 1

Version 2 replaced lsp-mode with Eglot.  If you are not ready for that,
version =1.1.2= is tagged and continues to work.

- lsp-mode, =dash= and =compat= are no longer dependencies; =eri= and
  Eglot are.  Any lsp-mode configuration for Lean can be removed.
- Diagnostics are reported through Flymake rather than Flycheck, since
  that is what Eglot drives.
- The ~lean4-keybinding-*~ options are gone.  Keys now live in
  ~lean4-mode-map~ and are rebound the ordinary way:
  =(keymap-set lean4-mode-map "C-c C-i" #'lean4-toggle-info)=.
- ~lean4-mode-hook~ is now an ordinary mode hook.  Whether the server
  starts automatically is controlled by ~lean4-auto-start-server~,
  which defaults to =t=.
- ~lean4-extra-arguments~ is now ~lean4-server-arguments~; the old name
  still works.
- Lean 3 autodetection is gone, along with ~lean4-autodetect-lean3~.  It
  ran =lean -v= every time a =.lean= file was opened.  Lean 3 users
  should use [[https://github.com/leanprover/lean3-mode][Lean3-Mode]].

* Usage

Opening a file with the =.lean= extension shows "Lean 4" in the
mode-line and starts the language server.  Files inside a Lake package
are served by =lake serve=, so the package's dependencies are on the
search path; a file outside one is served by =lean --server= using
whichever toolchain elan selects.

Type =#check id= and the word =#check= is underlined; point on =id=
reports its type through ElDoc.

The =*Lean Goal*= buffer, the counterpart of the Info-View pane in VS
Code, appears by itself and shows the proof state at point.  It is
displayed, not selected, so point stays in the file.  =C-c C-i= hides
and shows it, and ~lean4-info-auto-open~ turns the automatic opening
off.

Where it appears is up to =display-buffer-alist=, as for any other
buffer.  To put it in a side window on the right:

#+begin_src elisp
(add-to-list 'display-buffer-alist
             '("\\`\\*Lean Goal\\*\\'"
               (display-buffer-in-side-window)
               (side . right)
               (window-width . 0.4)))
#+end_src

** Keys in the goal display

Goals arrive as trees in which every subterm is labelled, so point can
rest on any part of a goal and ask about it.

| Key            | Description                                    | Command                           |
|----------------+------------------------------------------------+-----------------------------------|
| =RET=          | Press the control at point, or go to a message's position | ~lean4-info-return~    |
| =M-.=          | Jump to the definition of the subterm at point  | ~xref-find-definitions~           |
| =C-c C-t=      | Jump to the definition of its type             | ~lean4-info-goto-type-definition~ |
| =TAB=          | Fold or unfold the trace or section at point   | ~lean4-info-toggle-fold~          |
| =C-c C-s=      | Pin this position, or unpin the section point is in | ~lean4-info-toggle-pin~      |
| =C-c C-SPC=    | Pause or unpause the display                   | ~lean4-info-toggle-pause~         |
| =C-c C-g=      | Bring a paused display up to date              | ~lean4-info-refresh-paused~       |
| =C-c C-a=      | Pause or unpause the file's message list       | ~lean4-info-toggle-all-messages-pause~ |
| =C-c C-o=      | Order that list by position or by nearness     | ~lean4-info-toggle-message-order~ |

Pinning a position keeps it on display as a section of its own, above
the section following point, and any number of positions can be pinned.
Each keeps updating: a pin is a marker, so it follows its declaration as
the file is edited, and it stays on display after moving to another
file.  Each pinned section has its own controls -- one back to the position,
one to pause it, one to bring it up to date while paused, and one to
unpin it.  Pausing a pin is separate from pinning it: a pinned goal
follows its declaration through an edit unless told otherwise.  Pinning happens at point, so the followed
section is left out until point moves, rather than showing the same
position twice; returning to a pinned position later does show both.

Every control has a key and a menu entry as well, so none of them needs
a mouse.  The menu entries are the same in the Lean menu and in the goal
display's own, since every one of these commands works from either
buffer; each says what pressing it will do next, so an item reads
"Unpin this position" where the position is already pinned.
With several pins there is no one pin for a key to mean, so
=C-c C-s= means the section point is standing in: inside a pinned
section it unpins that one, and anywhere else it pins or unpins the
position point is on in the Lean buffer.  =C-c C-SPC= and =C-c C-g= read the same way: inside a
pinned section they pause and refresh that section, anywhere else the
one following point.  =RET= reaches the two things in the display that
lead anywhere: on a control it does what clicking it would, and on a
message heading it goes to the place the message was reported for.
Every control is therefore reachable without a mouse.

The last two are bound here as well as in the Lean buffer, so the
display can be pinned or paused without leaving it.  Clicking their
controls does the same, and leaves the keyboard in the Lean buffer
rather than taking focus, as VS Code does.  Both states can hold at
once, and the heading says so: pinned means the display has stopped
following point, paused that it has stopped updating at all.

Where there is nothing at point to report -- outside a proof, say -- the
display says =No info found.= rather than going blank, which would read
like a display that had stopped working.  Messages from elsewhere in the
file are still listed below it.

The type and docstring of the subterm at point are reported through
ElDoc, so they appear wherever ElDoc is configured to put them: the
echo area by default, or a child frame with a package such as
=eldoc-box=.

Traces fold like everything else, being sections themselves: =TAB= or
the mouse, with the same indicator.  Lean does not send the children of
a trace node until something asks -- a =simp= trace on a real proof is
enormous -- so opening one fetches them, once.

** The tactic state

The goals at point are listed under =Tactic state=, with the number of
them on the line below, both as VS Code words and places them.  A single
goal is counted too -- =1 goal= -- so the line is there on every proof
rather than only on a branching one.

A finished proof reads =goals accomplished= instead, which is Lean's own
wording for it; VS Code says =No goals= there and counts nothing, and
neither does this.

The expected type at point follows, under =Expected type=, and is not
counted -- VS Code counts only the tactic state.  Neither heading takes
a colon, as neither does in VS Code.

** Copying what is on display

| Command                      | Copies                                       |
|------------------------------+----------------------------------------------|
| ~lean4-info-copy-state~      | the tactic state, to the kill ring           |
| ~lean4-info-copy-to-comment~ | the tactic state, into the Lean buffer       |
| ~lean4-info-copy-message~    | the message point is in, to the kill ring    |

The first two are in both menus and work from either buffer; the third
needs point to be inside a message in the goal display, messages being
sections.  ~lean4-info-copy-to-comment~ puts the state in a =/- -/= block
above the line point is on, indented with it, as VS Code's "Copy Contents
to Comment" does.

The state is copied in full, whatever the settings above are hiding: text
pasted into an issue is no use with half the hypotheses missing.  This is
what VS Code copies too.

** How much of a goal to show

A goal in Mathlib can carry more hypotheses than fit on a screen, most of
them typeclass instances nobody is reasoning about.  Eight settings decide
how much of one is shown, the same eight VS Code gathers behind the cog in
its InfoView.  They are in the =Lean= menu and the goal display's own,
under =How much of a goal to show=, as checkboxes; each is also a command
and an option.

| Setting                                     | Default | Command                                          |
|---------------------------------------------+---------+--------------------------------------------------|
| ~lean4-info-show-goal-names~                | =t=     | ~lean4-info-toggle-goal-names~                   |
| ~lean4-info-emphasize-first-goal~           | =nil=   | ~lean4-info-toggle-emphasize-first-goal~         |
| ~lean4-info-target-first~                   | =nil=   | ~lean4-info-toggle-target-first~                 |
| ~lean4-info-hide-type-assumptions~          | =nil=   | ~lean4-info-toggle-type-assumptions~             |
| ~lean4-info-hide-instance-assumptions~      | =nil=   | ~lean4-info-toggle-instance-assumptions~         |
| ~lean4-info-hide-inaccessible-assumptions~  | =nil=   | ~lean4-info-toggle-inaccessible-assumptions~     |
| ~lean4-info-hide-let-values~                | =nil=   | ~lean4-info-toggle-let-values~                   |
| ~lean4-info-expected-type-visibility~       | =expanded= | ~lean4-info-cycle-expected-type~              |

Every default is VS Code's, so out of the box the whole goal is shown.
The commands change a setting for the session; customizing it makes the
change stick.

- Goal names are the =case inl= labels a structured proof produces.
- Emphasizing the first goal draws the others smaller and dimmer -- the
  main goal is the one being worked on, the rest are context.
- Showing the target first puts =⊢= above the hypotheses, and reverses
  them, so that the target stays next to the hypothesis it was next to.
- Type assumptions are hypotheses that are themselves types, such as the
  implicit =α : Type= of a general lemma.  Instance assumptions are
  typeclass instances, =[Inhabited α]= and its kind.  Hiding either drops
  the hypothesis entirely.
- Inaccessible assumptions are the ones Lean prints with a dagger, =h✝=,
  which cannot be referred to by name.  They are dimmed rather than
  hidden by default.  Where a dagger name shares a line with a usable
  one, hiding takes away just the name.
- Hiding let-values shows a =let= binder's type but not its value, which
  on a large value is the difference between reading the goal and
  scrolling past it.
- The expected type can be shown, shown folded, or left out.  The middle
  two are defaults rather than rules: the section still folds and unfolds
  with =TAB=, and a fold made by hand survives until the setting changes.

Goals are kept as Lean sent them and rendered on the way into the
buffer, so changing one of these costs a redraw rather than another
request.  That is what lets a change reach a pinned or paused section,
where re-fetching would be precisely the wrong thing.  Goals from a
server too old for the interactive RPC arrive as text and cannot be
filtered; the settings simply have nothing to act on.

** Errors and warnings

Diagnostics are reported through Flymake, which Eglot drives.  =C-c ! n=
and =C-c ! p= move between them, and ~flymake-show-buffer-diagnostics~
lists them.

Not everything Lean sends is a problem.  It reports a completed proof,
trace output and whatever a project's own tactics emit at note severity,
all of which is meant for the goal display; flagging it in the editor
buries the errors among it.  So Flymake is shown errors and warnings,
and the rest goes to the goal display only.  Set
~lean4-flymake-minimum-severity~ to =note= to be shown everything, as VS
Code's Problems view does, or to =error= for less.

Messages appear in the goal display placed by Lean's own notion of
which declaration they belong to, so a message about a multi-line
declaration stays visible while point moves through it.  Terms inside a
message are as interactive as terms inside a goal.

Those covering point are listed under =Messages=, set in under the
heading naming the position, along with the goals and the expected type.
Every message in the file is listed under =All messages=, at the outer
level, with two controls of its own: one orders the list by nearness to point or by
position in the file -- nearness first by default, as in VS Code, whose
manual has All Messages "sorted by their proximity to the text cursor by
default" -- and one holds the list as it is, separately from the pause in
the position heading.  While the display is paused a third control
appears in the position heading, between the way back to the pinned
position and the pin, which brings it up to date without unpausing it.  Both headings count what is in them by severity, the way VS
Code's do -- =All messages (1 ⊗  5 ⓘ)= for a file with one error and
five notes.

Messages Lean marks as being for the goal display rather than the
editor -- that is what =isSilent= means, the completed-proof report
among them -- are shown against the position they belong to and kept out
of both Flymake and =All messages=, as VS Code does with them.

Lean emits three severities: error =⊗=, warning =⚠= and information
=ⓘ=.  LSP defines a fourth, hint, which this package draws as =ⓗ=, but
Lean's own ~MessageSeverity~ has no such value and its server never
sends one.  The glyphs are picked for the frame, falling back to =E W I
H= where none can be displayed.

Each message is a section of its own, so a long one -- a =simp= trace, a
mismatch between two large terms -- folds away without folding the rest.
Sections are set in with spaces and their fold indicators drawn by
~magit-section~, in the fringe, the way a Magit buffer does both.
Its heading names the file, line and column, and carries an =↪= control,
right-aligned, that sends point there.  Clicking works as =mouse-1= does
throughout Emacs: on a control it acts, and anywhere else it moves
point -- which is how a subterm is put under ElDoc, and how VS Code
reads a plain click too.  =RET= does the same two things by keyboard,
going to the message's position from anywhere on its heading; the
definition of a subterm is =M-.=, wherever your xref frontend puts it.
Folding is =TAB=, and by mouse whatever
~magit-section~ itself offers -- a double click, or a click on the
fringe or margin, from version 4; nothing in 3.3.0 -- so this display
folds the way your Magit does.  The same control appears in the
top heading, but only while pinned: unpinned, the display is following
point and it would only lead where point already is.

** Building dependencies

Visiting a file does not build what it imports.  The server decides that
from a field on the notification announcing the file, and =C-c C-d=
(~lean4-refresh-file-dependencies~) is what asks for a build: it closes
and reopens the file, telling Lean to build a dependency that is out of
date on the way.  That is the command to reach for after editing an
import, or when the goal display reports an import that cannot be found.
VS Code calls it "Server: Restart File".

The build happens once.  If the file worker then crashes, reopening the
file does not set the build going again -- a distinction worth having on a
file whose imports do not compile, where the alternative is a rebuild per
crash.

Set ~lean4-automatically-build-dependencies~ to =t= to build on every
open instead, as VS Code's ~lean4.automaticallyBuildDependencies~ does.
Both default off for the same reason: on a project the size of Mathlib,
opening one file to read it should not commit you to building everything
beneath it.  =C-c C-p C-l= (~lean4-lake-build~) builds the package
outright.

** Building

=C-c C-p C-l= (~lean4-lake-build~) builds the package the way VS Code's
"Build Project" does, which is three steps rather than a bare =lake
build=:

1. =lake resolve-deps= clones a dependency the manifest names but the
   checkout has not got.
2. =lake exe cache get= downloads Mathlib's build artefacts, where that
   executable exists -- see [[*Mathlib's build cache]].  On a project that
   depends on Mathlib this is the step between minutes and hours.
3. =lake build= builds what is left.

Each step is conditional on the one before, so a failure stops the rest,
and all three report into one compilation buffer where =M-x next-error=
walks whatever any of them said.

The cache step is skipped, without complaint, in a project that has no
=cache= executable -- most projects.  A cache download that /fails/,
though, stops the build rather than leaving it to do that work locally.

For a bare =lake build=, with no network and no dependency resolution,
=M-x compile= is the thing.

** Mathlib's build cache

Mathlib is far too large to build locally, and does not need to be: its
artifacts are built upstream and can be downloaded.  Three commands ask
for them, all through =lake exe cache get=, which is Mathlib's own
executable rather than anything Lake provides -- so in a project that
does not depend on Mathlib they fail, and Lake says so in the
compilation buffer.

| Key           | Description                             | Command                             |
|---------------+-----------------------------------------+-------------------------------------|
| =C-c C-p C-c= | The whole package                       | ~lean4-lake-fetch-cache~            |
| =C-c C-p C-f= | This file and what it imports           | ~lean4-lake-fetch-file-cache~       |
|               | Every open Lean file in the package     | ~lean4-lake-fetch-open-file-caches~ |

The last is in the Lean menu, under =Project=, along with the other two
and =lake build=.  Fetching for one file is much quicker than for the
whole of Mathlib and is usually what is wanted; fetching for the package
is the thing to run once, after cloning.

Output goes to a compilation buffer, so =M-x next-error= walks whatever
Lake reports, as with any other build.

** Choosing which Lean to use

Four commands, in the =Lean= menu under =Lean version=.

| Command                            | Sets                                     |
|------------------------------------+------------------------------------------|
| ~lean4-select-project-toolchain~   | this project's =lean-toolchain=          |
| ~lean4-select-default-toolchain~   | the version used outside any project     |
| ~lean4-update-release-channel~     | fetches a channel's newest version       |
| ~lean4-uninstall-toolchains~       | removes installed versions               |

All four need elan 4 or later, which is where =elan dump-state= arrives;
VS Code requires the same, for the same reason -- without it the versions
cannot be listed with what elan has resolved them to.

The versions offered are not only the ones installed.  As VS Code does,
=release.lean-lang.org= is asked for the stable, beta and nightly
releases too, so a version you have not got can be chosen and elan
fetches it; each is marked =(installed)= or =(not installed)=.  Being
unable to reach that list is a warning, not a failure: what is installed
is still worth offering.  Releases are listed newest first, with a release
above the candidates that led to it.

Only ~lean4-select-default-toolchain~ offers =leanprover/lean4:stable=,
the channel meaning "whatever is newest".  A project pins a version
instead, which is the same distinction VS Code draws.

~lean4-update-release-channel~ offers only the channels actually behind,
showing what each is installed at and what it would become, and says so
where none are.  ~lean4-uninstall-toolchains~ marks each version as unused
or names the projects still using it, from =elan toolchain gc=; it takes
several at once, comma-separated.

Each asks before acting.  Setting a project's version asks hardest, and
the warning is VS Code's: it is meant for maintainers of a project, and
changing it can break not only the project's own code but its lakefile and
its Lake dependencies.  To take a dependency's version instead, in order
to stay compatible with it, ~lean4-lake-update-dependency~ is the command
to use.

*** Elan itself

Three more commands manage the tool rather than the versions.

~lean4-install-elan~ fetches and runs the installer from
=elan.lean-lang.org=, which is what VS Code does and what Lean's [[https://lean-lang.org/lean4/doc/setup.html][setup
guide]] describes.  It shows the exact command and asks before running it,
since this downloads a script and executes it; output goes to a
compilation buffer.  It refuses where elan is already installed.  Emacs
will not find the new elan until the environment it was started with is
refreshed, which usually means restarting Emacs.

~lean4-update-elan~ runs =elan self update=.

~lean4-uninstall-elan~ runs =elan self uninstall=, which takes every
installed Lean version with it -- so every project on the machine loses
the Lean it was using, and Lean and Lake leave the =PATH=.  It asks
twice.

~lean4-install-toolchain~ downloads a version without making it the
default, for fetching one ahead of needing it; choosing a =(not
installed)= version in any of the other commands fetches it anyway.

** Searching Mathlib with Loogle

=M-x lean4-loogle-search= asks [[https://loogle.lean-lang.org][Loogle]], which searches Mathlib by shape
rather than by name:

- =Nat.succ_le_succ= finds the declaration of that name.
- =?a + ?b = ?b + ?a= finds the commutativity lemmas.
- =Real.sin, Real.cos= finds what mentions both.
- A query beginning with a turnstile, =|-= followed by a pattern, finds
  what /concludes/ a statement of that shape.

Loogle's own page documents the syntax.

The query is read with the Lean input method inherited, so =lpha= becomes
α in the minibuffer exactly as it would in a Lean buffer -- which is the
point of asking from inside Emacs rather than in a browser tab, since
Loogle's syntax leans on notation.  An active region is offered as the
starting point.

Results appear in a =*Lean Loogle*= buffer: each is its name, the module it
lives in, and its type, foldable like everything else.  Where Loogle offers
a spelling suggestion it is a button that searches for it instead.

| Key   | Description                                    | Command                            |
|-------+------------------------------------------------+------------------------------------|
| =RET= | Open the result's documentation in a browser   | ~lean4-loogle-browse-documentation~ |
| =w=   | Copy the result's name                         | ~lean4-loogle-copy-name~           |
| =g=   | Ask Loogle the same query again                | ~lean4-loogle-again~               |
| =q=   | Bury the buffer                                | ~quit-window~                      |

=RET= does what clicking a result's name does in VS Code.

This needs no Lean server and no project: Loogle is a web service, and it
answers about Mathlib rather than about the code in hand.
~lean4-loogle-url~ points elsewhere, for a Loogle of your own.

** The module hierarchy

What a module imports, and what imports it, as a tree in a
=*Lean Module Hierarchy*= buffer.

| Command                         | Shows                              |
|---------------------------------+------------------------------------|
| ~lean4-module-hierarchy~        | what this file's module imports    |
| ~lean4-module-hierarchy-inverse~ | what imports this file's module   |
| ~lean4-module-copy-name~        | copies the module's name           |

All three are in the =Lean= menu under =Module hierarchy=.  VS Code binds
its two to =Alt+Shift+M= and =Alt+Shift+N=; no keys are bound here, those
chords not being Emacs ones, so bind them to taste:

#+begin_src elisp
(keymap-set lean4-mode-map "C-c C-p C-m" #'lean4-module-hierarchy)
#+end_src

The buffer is a ~magit-section~ tree, so it folds with =TAB= and moves the
way the goal display does.

| Key   | Description                          | Command                 |
|-------+--------------------------------------+-------------------------|
| =RET= | Visit the file of the module at point | ~lean4-module-visit~    |
| =TAB= | Fold or unfold the node at point      | ~magit-section-toggle~  |
| =g=   | Ask for the tree again                | ~lean4-module-refresh~  |
| =q=   | Bury the buffer                       | ~quit-window~           |

A level is fetched when it is opened, not before: Mathlib's import graph
is far too large to ask for at once.  An unopened node shows =...= until
its children arrive.  A module that already appears further up the tree is
marked =(shown above)= and not expanded, since the import graph has
diamonds and following one would go round for ever.

Imports of a module using Lean's =module= keyword carry modifiers, and
those are shown beside the name: =private=, =all=, =meta=, or =meta and
non-meta= for one imported both ways.

*** It needs a built project

The server answers these from its reference data, which it builds from the
=.ilean= files a build leaves behind.  In a project that has not been
built the tree is empty -- correctly so, there being nothing indexed to
report.  Run =C-c C-p C-l= (~lean4-lake-build~), or
=C-c C-p C-c= (~lean4-lake-fetch-cache~) on a Mathlib project, first.

~lean4-enable-file-watchers~ is off by default, so a tree fetched after a
rebuild may be the one from before it; =g= asks again.

** Other Lake operations

Two more commands live in the same =Project= menu.

~lean4-lake-clean~ runs =lake clean=, and asks first: on a project the
size of Mathlib that discards hours of building, though
~lean4-lake-fetch-cache~ gets most of it back.

~lean4-lake-update-dependency~ runs =lake update= on one dependency,
offering the package's direct Git dependencies for completion -- read
from =lake-manifest.json=, which is Lake's record of what it resolved
them to.  It asks first too, and means it: VS Code's warning is that the
command is for maintainers of a project, and that if the new version is
incompatible with another dependency or with the code here, the project
may stop building.  It also rewrites the manifest, which most projects
keep under version control.

Unlike VS Code it leaves =lean-toolchain= alone.  VS Code offers to match
it to the updated dependency's; that is a second decision, about a file
both Lake and elan read, and is better made deliberately.

Opening a project needs nothing from this package: a Lean file is served
by whichever workspace encloses it, so =C-x C-f= and =project.el= are the
whole of it.  VS Code's "Open Local Project" exists because it has a
window to point at a folder.

** Completion

Completion is offered through ~completion-at-point-functions~, so any
completion interface works: the default =*Completions*= buffer,
=company=, =corfu= or anything else.  Three sources are active in a Lean
buffer.  Eglot's is one.  Another is for the Unicode abbreviations, so
that typing =\al= offers =\alpha= and inserting it produces α.  The
third is for Lean's keywords, because the server's own completion is
contextual and offers nothing towards a bare word at the top level:
=exam= gets no help towards =example= from Lean, and VS Code fills the
same gap with editor-level word suggestions.

None of the three is exclusive, Eglot's included -- its entry is
rewrapped to say so.  Left as Eglot leaves it, a prefix the server had
nothing for ended completion there instead of falling through to
whatever else you have configured.

Typing an abbreviation in full still works without completion: the Lean
input method replaces it as soon as it is unambiguous.

* Configuration

Lean4-Mode uses [[https://www.gnu.org/software/emacs/manual/html_node/eglot/][Eglot]], the LSP client built into Emacs 29 and later, so
Eglot's own configuration applies.

** Frequently used options

- ~lean4-auto-start-server~ (default =t=) -- whether visiting a Lean
  file starts the language server.  Set to =nil= to start it by hand
  with =M-x eglot=.
- ~lean4-info-auto-open~ (default =t=) -- whether the goal display
  appears when a Lean file is opened, as VS Code's InfoView does.
- ~lean4-info-interactive~ (default =t=) -- whether to fetch goals over
  Lean's interactive RPC.  With =nil=, goals are plain text and cannot
  be hovered or jumped from.
- ~lean4-indent-offset~ (default =2=) -- columns per level of
  indentation.
- ~lean4-indent-function~ -- ~lean4-indent-line~ guesses from the layout
  and cycles when pressed again; ~eri-indent~ does not guess and only
  cycles, which is what this mode did before version 2.
- ~lean4-enable-file-watchers~ (default =nil=) -- whether to honour the
  server's request to watch every =*.ilean= file.  On a project the size
  of Mathlib that is tens of thousands of files.
- ~lean4-automatically-build-dependencies~ (default =nil=) -- whether
  visiting a file may build the dependencies it imports.  See [[*Building
  dependencies]].
- ~lean4-server-arguments~ -- extra arguments for the language server.
- ~lean4-workspace-roots~ and ~lean4-workspace-exclusions~ -- directories
  to treat as workspace roots, and directories in which never to start a
  server.

** The goal display's controls

Each control says what clicking it will do rather than what the state
is, so both swap glyph when engaged: =📌= becomes =📍= once pinned, and
=⏸= becomes =⏵= once paused.  The pin is the same pin seen head-on
instead of from the side -- pushed in rather than held ready.  VS Code
turns its pin from upright to flat to say the same thing, but that is a
codicon font; Unicode's one upright/slanted pin pair needs U+1F588,
which too many fonts draw as a box to rest the difference on.  The
engaged control is faced differently too, which is what carries the
state on a frame with no second glyph to swap to.

The glyphs are chosen for whichever frame they are drawn in, decided
each time rather than once at startup, so one Emacs serving both a
graphical frame and a terminal gets the right thing in each.  A
graphical frame usually gets =📌 📍 ⏸ ⏵=, a terminal =⌖ ⌾ ⏸ ⏵=, and a
display with nothing but ASCII gets =P [P] || >=.  Set
~lean4-info-pin-icon~, ~lean4-info-unpin-icon~, ~lean4-info-pause-icon~
or ~lean4-info-resume-icon~ to override.

** Older Lean versions

Some of what this package reads was added to the Lean server over time,
and it degrades quietly where a field is absent.

Lean marks messages meant for the goal display rather than the editor,
and marks a finished declaration with a tag.  Servers older than those
fields -- 4.26 sets neither, even when asked -- send the completed-proof
report as an ordinary note, so it is the severity filter above rather
than the tag that keeps it out of the editor there.  The marker in the
goal display needs the tag, and is simply absent without it.

Interactive references are encoded in a format negotiated with the
server; version 1 arrived in Lean 4.30.  Older servers keep to version
0, which this package reads too.  =M-x lean4-diagnose= reports which
extensions the running server offers.

** Semantic highlighting

What counts as a keyword in Lean is settled by the elaborator rather
than by the syntax, so the server is the only thing that can say.  It
reports its findings as LSP semantic tokens, and gives =sorry= and the
other proof-admitting syntax a token type of its own,
=leanSorryLike=.  Eglot gained support for these in version 1.20, which
is newer than the Eglot bundled with Emacs 29 (1.12) or Emacs 30
(1.17).  Lean4-Mode uses it when it is available and says nothing when
it is not, so

: M-x package-install RET eglot RET

turns on semantic highlighting on any supported Emacs.

Expect keywords rather than colour for every identifier.  The server
advertises the whole standard set of token types but, as of Lean 4.32,
sends little beyond keywords and =leanSorryLike=; put point on the
=rfl= in

#+begin_src lean
theorem proved : 1 + 1 = 2 := by
  rfl
#+end_src

and =M-:= =(get-text-property (point) 'face)= answers
=eglot-semantic-keyword=.  Nothing here could have known that: =rfl= is
a keyword because the elaborator says so, and =M-x
eglot-semantic-tokens-mode= to turn it off leaves it uncoloured.

** Optional packages

None of these are required, and none are declared as dependencies.

- =markdown-mode= -- renders docstrings in hover popups.
- =eldoc-box= -- shows ElDoc output in a child frame rather than the
  echo area.
- =company= or =corfu= -- a completion interface.
- =consult-eglot= -- searching workspace symbols.

* Troubleshooting

=M-x lean4-diagnose= reports how things are set up: the versions of
Emacs and of each dependency, the Lean and Lake executables it found,
the workspace root and its toolchain, the command used to start the
server and whether one is running, and the diagnostics currently in the
buffer with Lean's own fields on each.  It reports on a Lean buffer even
when run from somewhere else.

Include its output when reporting a problem; the counterpart in VS Code
is "Troubleshooting: Show Setup Information".

* Common Pitfalls

Lean4-Mode only supports version 4 of Lean.  For editing Lean version
3, use [[https://github.com/leanprover/lean3-mode][Lean3-Mode]], which is also known as Lean-Mode due to historical
reasons.  In principle, it is fine to have both Lean3-Mode and
Lean4-Mode installed at the same time.  But note that Lean3-Mode uses
the prefix =lean-= for its symbols.  E.g. you should not use
=lean-=-prefixed commands in a buffer with Lean4-Mode as major mode.
