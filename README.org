#+texinfo_dir_desc: Emacs major mode for Lean language

This package extends [[https://www.gnu.org/software/emacs/][GNU Emacs]] by providing a major mode for editing
code written in version 4 of the programming language and theorem
prover [[https://lean-lang.org][Lean]].

The Lean4-Mode source code is developed at [[https://github.com/d-torrance/lean4-mode][Github]] and its issues
tracked there too.  Further discussions and question-answering takes
place in the [[https://leanprover.zulipchat.com/#narrow/channel/468104-Emacs][#Emacs channel]] of Lean's Zulip chat.

This continues the [[https://github.com/leanprover-community/lean4-mode][lean4-mode]] developed under the
leanprover-community organization; see [[*Acknowledgements]].

For legacy version 3 of Lean, use the archived [[https://github.com/leanprover/lean3-mode][Lean3-Mode]] (also known
as /Lean-Mode/).

* Installation

** Requirements

- [[https://lean-lang.org/lean4/doc/setup.html][Lean]] version 4, normally installed through [[https://github.com/leanprover/elan][elan]]
- GNU Emacs version 29.1 or later
- The Emacs packages [[https://github.com/agda/agda][eri]] and [[https://github.com/magit/magit/blob/main/lisp/magit-section.el][magit-section]], both on [[https://melpa.org/#/getting-started][Melpa]]

Eglot is used for the language-server connection, and is built into
Emacs 29 and later, so nothing needs installing for it.  See
[[*Semantic highlighting]] for one feature that a newer Eglot than the
bundled one provides.

magit-section 3.3.0 is enough, and is what Debian and Ubuntu ship as
=elpa-magit-section=.  If you have it, do not install a newer one on
this package's account: Magit depends on the matching version of
magit-section, so upgrading only that one breaks Magit.  Both versions
are tested, including against a live Lean server.

** From source

Clone the repository and add it to the ~load-path~:

#+begin_src elisp
(add-to-list 'load-path "~/path/to/lean4-mode")
#+end_src

Lean4-Mode is then enabled automatically for files with the =.lean=
extension.  Loading it eagerly is only necessary in order to customize
variables before a Lean file is opened:

#+begin_src elisp
(require 'lean4-mode)
#+end_src

** With a source-based package manager

List the ="data"= directory in the recipe: it holds the table of
Unicode abbreviations, without which the input method has nothing to
offer.  If loading is deferred, specify ~lean4-mode~ as a =:command=.

*** Native =:vc= (Emacs 30 or later)

#+begin_src elisp
(use-package lean4-mode
  :commands lean4-mode
  :vc (:url "https://github.com/d-torrance/lean4-mode.git"
       :rev :last-release
       ;; Or, for the bleeding edge:
       ;; :rev :newest
       ))
#+end_src

*** Doom-Emacs

#+begin_src elisp
(package! lean4-mode
  :recipe (:host github
           :repo "d-torrance/lean4-mode"
           :files ("*.el" "data")))
#+end_src

*** Straight

#+begin_src elisp
(use-package lean4-mode
  :commands lean4-mode
  :straight (lean4-mode :type git :host github
                        :repo "d-torrance/lean4-mode"
                        :files ("*.el" "data")))
#+end_src

** Upgrading from version 1

Version 2 replaced lsp-mode with Eglot.  If you are not ready for that,
version =1.1.2= is tagged and continues to work.

- lsp-mode, =dash= and =compat= are no longer dependencies; =eri= and
  Eglot are.  Any lsp-mode configuration for Lean can be removed.
- Diagnostics are reported through Flymake rather than Flycheck, since
  that is what Eglot drives.
- The ~lean4-keybinding-*~ options are gone.  Keys now live in
  ~lean4-mode-map~ and are rebound the ordinary way:
  =(keymap-set lean4-mode-map "C-c C-i" #'lean4-toggle-info)=.
- ~lean4-mode-hook~ is now an ordinary mode hook.  Whether the server
  starts automatically is controlled by ~lean4-auto-start-server~,
  which defaults to =t=.
- ~lean4-extra-arguments~ is now ~lean4-server-arguments~; the old name
  still works.
- Lean 3 autodetection is gone, along with ~lean4-autodetect-lean3~.  It
  ran =lean -v= every time a =.lean= file was opened.  Lean 3 users
  should use [[https://github.com/leanprover/lean3-mode][Lean3-Mode]].

* Usage

Opening a file with the =.lean= extension shows "Lean 4" in the
mode-line and starts the language server.  Files inside a Lake package
are served by =lake serve=, so the package's dependencies are on the
search path; a file outside one is served by =lean --server= using
whichever toolchain elan selects.

Type =#check id= and the word =#check= is underlined; point on =id=
reports its type through ElDoc.

The =*Lean Goal*= buffer, the counterpart of the Info-View pane in VS
Code, appears by itself and shows the proof state at point.  It is
displayed, not selected, so point stays in the file.  =C-c C-i= hides
and shows it, and ~lean4-info-auto-open~ turns the automatic opening
off.

Where it appears is up to =display-buffer-alist=, as for any other
buffer.  To put it in a side window on the right:

#+begin_src elisp
(add-to-list 'display-buffer-alist
             '("\\`\\*Lean Goal\\*\\'"
               (display-buffer-in-side-window)
               (side . right)
               (window-width . 0.4)))
#+end_src

** Keys in a Lean buffer

| Key                    | Description                                              | Command                           |
|------------------------+----------------------------------------------------------+-----------------------------------|
| =C-c C-i=              | Show or hide the goal display                            | ~lean4-toggle-info~               |
| =C-c C-s=              | Pin the goal display to point, or unpin it               | ~lean4-info-toggle-pin~           |
| =C-c C-SPC=            | Pause or unpause the goal display                        | ~lean4-info-toggle-pause~         |
| =C-c C-k=              | Echo the keystroke needed to input the symbol at point    | ~quail-show-key~                  |
| =C-c C-d=              | Recompile and reload imports                             | ~lean4-refresh-file-dependencies~ |
| =C-c C-r=              | Restart the language server                              | ~eglot-reconnect~                 |
| =C-c C-x= or =C-c C-l= | Execute Lean in stand-alone mode                         | ~lean4-std-exe~                   |
| =C-c C-p C-l=          | Build the package with Lake                              | ~lean4-lake-build~                |
| =TAB=                  | Indent, cycling through the alternatives when pressed again | ~lean4-tab-indent~             |

** Keys in the goal display

Goals arrive as trees in which every subterm is labelled, so point can
rest on any part of a goal and ask about it.

| Key            | Description                                    | Command                           |
|----------------+------------------------------------------------+-----------------------------------|
| =M-.= or =RET= | Act on the thing at point                      | ~lean4-info-return~               |
| =C-c C-t=      | Jump to the definition of its type             | ~lean4-info-goto-type-definition~ |
| =TAB=          | Fold or unfold the trace or section at point   | ~lean4-info-toggle-fold~          |
| =C-c C-s=      | Pin this position, or unpin the section point is in | ~lean4-info-toggle-pin~      |
| =C-c C-SPC=    | Pause or unpause the display                   | ~lean4-info-toggle-pause~         |
| =C-c C-g=      | Bring a paused display up to date              | ~lean4-info-refresh-paused~       |
| =C-c C-a=      | Pause or unpause the file's message list       | ~lean4-info-toggle-all-messages-pause~ |
| =C-c C-o=      | Order that list by position or by nearness     | ~lean4-info-toggle-message-order~ |

Pinning a position keeps it on display as a section of its own, above
the section following point, and any number of positions can be pinned.
Each keeps updating: a pin is a marker, so it follows its declaration as
the file is edited, and it stays on display after moving to another
file.  Each pinned section has its own controls -- one back to the position,
one to pause it, one to bring it up to date while paused, and one to
unpin it.  Pausing a pin is separate from pinning it: a pinned goal
follows its declaration through an edit unless told otherwise.  Pinning happens at point, so the followed
section is left out until point moves, rather than showing the same
position twice; returning to a pinned position later does show both.

Every control has a key and a menu entry as well, so none of them needs
a mouse.  With several pins there is no one pin for a key to mean, so
=C-c C-s= means the section point is standing in: inside a pinned
section it unpins that one, and anywhere else it pins or unpins the
position point is on in the Lean buffer.  =C-c C-SPC= and =C-c C-g= read the same way: inside a
pinned section they pause and refresh that section, anywhere else the
one following point.  =RET= acts on whatever is under point: a control does what
clicking it would, a message heading goes to the place it was reported for, and a
term goes to its definition.  Every control is therefore reachable
without a mouse.

The last two are bound here as well as in the Lean buffer, so the
display can be pinned or paused without leaving it.  Clicking their
controls does the same, and leaves the keyboard in the Lean buffer
rather than taking focus, as VS Code does.  Both states can hold at
once, and the heading says so: pinned means the display has stopped
following point, paused that it has stopped updating at all.

Where there is nothing at point to report -- outside a proof, say -- the
display says =No info found.= rather than going blank, which would read
like a display that had stopped working.  Messages from elsewhere in the
file are still listed below it.

The type and docstring of the subterm at point are reported through
ElDoc, so they appear wherever ElDoc is configured to put them: the
echo area by default, or a child frame with a package such as
=eldoc-box=.

Traces fold like everything else, being sections themselves: =TAB= or
the mouse, with the same indicator.  Lean does not send the children of
a trace node until something asks -- a =simp= trace on a real proof is
enormous -- so opening one fetches them, once.

** Errors and warnings

Diagnostics are reported through Flymake, which Eglot drives.  =C-c ! n=
and =C-c ! p= move between them, and ~flymake-show-buffer-diagnostics~
lists them.

Not everything Lean sends is a problem.  It reports a completed proof,
trace output and whatever a project's own tactics emit at note severity,
all of which is meant for the goal display; flagging it in the editor
buries the errors among it.  So Flymake is shown errors and warnings,
and the rest goes to the goal display only.  Set
~lean4-flymake-minimum-severity~ to =note= to be shown everything, as VS
Code's Problems view does, or to =error= for less.

Messages appear in the goal display placed by Lean's own notion of
which declaration they belong to, so a message about a multi-line
declaration stays visible while point moves through it.  Terms inside a
message are as interactive as terms inside a goal.

Those covering point are listed under =Messages=, set in under the
heading naming the position, along with the goals and the expected type.
Every message in the file is listed under =All messages=, at the outer
level, with two controls of its own: one orders the list by nearness to point or by
position in the file -- nearness first by default, as in VS Code, whose
manual has All Messages "sorted by their proximity to the text cursor by
default" -- and one holds the list as it is, separately from the pause in
the position heading.  While the display is paused a third control
appears in the position heading, between the way back to the pinned
position and the pin, which brings it up to date without unpausing it.  Both headings count what is in them by severity, the way VS
Code's do -- =All messages (1 ⊗  5 ⓘ)= for a file with one error and
five notes.

Messages Lean marks as being for the goal display rather than the
editor -- that is what =isSilent= means, the completed-proof report
among them -- are shown against the position they belong to and kept out
of both Flymake and =All messages=, as VS Code does with them.

Lean emits three severities: error =⊗=, warning =⚠= and information
=ⓘ=.  LSP defines a fourth, hint, which this package draws as =ⓗ=, but
Lean's own ~MessageSeverity~ has no such value and its server never
sends one.  The glyphs are picked for the frame, falling back to =E W I
H= where none can be displayed.

Each message is a section of its own, so a long one -- a =simp= trace, a
mismatch between two large terms -- folds away without folding the rest.
Sections are set in with spaces and their fold indicators drawn by
~magit-section~, in the fringe, the way a Magit buffer does both.
Its heading names the file, line and column, and carries an =↪= control,
right-aligned, that sends point there.  Clicking works as =mouse-1= does
throughout Emacs: on a control it acts, and anywhere else it moves
point -- which is how a subterm is put under ElDoc, and how VS Code
reads a plain click too.  =RET= reaches further, having no control under
a pointer to press: on a message heading it goes to the place the
message was reported for, and on a subterm to its definition.
Folding is =TAB=, and by mouse whatever
~magit-section~ itself offers -- a double click, or a click on the
fringe or margin, from version 4; nothing in 3.3.0 -- so this display
folds the way your Magit does.  The same control appears in the
top heading, but only while pinned: unpinned, the display is following
point and it would only lead where point already is.

** Completion

Completion is offered through ~completion-at-point-functions~, so any
completion interface works: the default =*Completions*= buffer,
=company=, =corfu= or anything else.  Two sources are active in a Lean
buffer -- Eglot's, and one for the Unicode abbreviations, so that typing
=\\al= offers =\\alpha= and inserting it produces α.

Typing an abbreviation in full still works without completion: the Lean
input method replaces it as soon as it is unambiguous.

* Configuration

Lean4-Mode uses [[https://www.gnu.org/software/emacs/manual/html_node/eglot/][Eglot]], the LSP client built into Emacs 29 and later, so
Eglot's own configuration applies.

** Frequently used options

- ~lean4-auto-start-server~ (default =t=) -- whether visiting a Lean
  file starts the language server.  Set to =nil= to start it by hand
  with =M-x eglot=.
- ~lean4-info-auto-open~ (default =t=) -- whether the goal display
  appears when a Lean file is opened, as VS Code's InfoView does.
- ~lean4-info-interactive~ (default =t=) -- whether to fetch goals over
  Lean's interactive RPC.  With =nil=, goals are plain text and cannot
  be hovered or jumped from.
- ~lean4-indent-offset~ (default =2=) -- columns per level of
  indentation.
- ~lean4-indent-function~ -- ~lean4-indent-line~ guesses from the layout
  and cycles when pressed again; ~eri-indent~ does not guess and only
  cycles, which is what this mode did before version 2.
- ~lean4-enable-file-watchers~ (default =nil=) -- whether to honour the
  server's request to watch every =*.ilean= file.  On a project the size
  of Mathlib that is tens of thousands of files.
- ~lean4-server-arguments~ -- extra arguments for the language server.
- ~lean4-workspace-roots~ and ~lean4-workspace-exclusions~ -- directories
  to treat as workspace roots, and directories in which never to start a
  server.

** The goal display's controls

Each control says what clicking it will do rather than what the state
is, so both swap glyph when engaged: =📌= becomes =📍= once pinned, and
=⏸= becomes =⏵= once paused.  The pin is the same pin seen head-on
instead of from the side -- pushed in rather than held ready.  VS Code
turns its pin from upright to flat to say the same thing, but that is a
codicon font; Unicode's one upright/slanted pin pair needs U+1F588,
which too many fonts draw as a box to rest the difference on.  The
engaged control is faced differently too, which is what carries the
state on a frame with no second glyph to swap to.

The glyphs are chosen for whichever frame they are drawn in, decided
each time rather than once at startup, so one Emacs serving both a
graphical frame and a terminal gets the right thing in each.  A
graphical frame usually gets =📌 📍 ⏸ ⏵=, a terminal =⌖ ⌾ ⏸ ⏵=, and a
display with nothing but ASCII gets =P [P] || >=.  Set
~lean4-info-pin-icon~, ~lean4-info-unpin-icon~, ~lean4-info-pause-icon~
or ~lean4-info-resume-icon~ to override.

** Older Lean versions

Some of what this package reads was added to the Lean server over time,
and it degrades quietly where a field is absent.

Lean marks messages meant for the goal display rather than the editor,
and marks a finished declaration with a tag.  Servers older than those
fields -- 4.26 sets neither, even when asked -- send the completed-proof
report as an ordinary note, so it is the severity filter above rather
than the tag that keeps it out of the editor there.  The marker in the
goal display needs the tag, and is simply absent without it.

Interactive references are encoded in a format negotiated with the
server; version 1 arrived in Lean 4.30.  Older servers keep to version
0, which this package reads too.  =M-x lean4-diagnose= reports which
extensions the running server offers.

** Semantic highlighting

Lean classifies identifiers during elaboration, and reports the result
as LSP semantic tokens.  Eglot gained support for these in version
1.20, which is newer than the Eglot bundled with Emacs 29 (1.12) or
Emacs 30 (1.17).  Lean4-Mode uses it when it is available and says
nothing when it is not, so

: M-x package-install RET eglot RET

turns on semantic highlighting on any supported Emacs.

** Optional packages

None of these are required, and none are declared as dependencies.

- =markdown-mode= -- renders docstrings in hover popups.
- =eldoc-box= -- shows ElDoc output in a child frame rather than the
  echo area.
- =company= or =corfu= -- a completion interface.
- =consult-eglot= -- searching workspace symbols.

* Troubleshooting

=M-x lean4-diagnose= reports how things are set up: the versions of
Emacs and of each dependency, the Lean and Lake executables it found,
the workspace root and its toolchain, the command used to start the
server and whether one is running, and the diagnostics currently in the
buffer with Lean's own fields on each.  It reports on a Lean buffer even
when run from somewhere else.

Include its output when reporting a problem; the counterpart in VS Code
is "Troubleshooting: Show Setup Information".

* Common Pitfalls

Lean4-Mode only supports version 4 of Lean.  For editing Lean version
3, use [[https://github.com/leanprover/lean3-mode][Lean3-Mode]], which is also known as Lean-Mode due to historical
reasons.  In principle, it is fine to have both Lean3-Mode and
Lean4-Mode installed at the same time.  But note that Lean3-Mode uses
the prefix =lean-= for its symbols.  E.g. you should not use
=lean-=-prefixed commands in a buffer with Lean4-Mode as major mode.
